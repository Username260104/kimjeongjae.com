# Kimjeongjae Wiki 구현 계획 검토 보고서

검토일: 2026-07-10  
검토 대상: `wiki-portfolio-research.md`, 기존 `wiki-visual-implementation-plan.md`, 현재 작업공간

## 결론

MediaWiki를 제외하고 정적 Wiki 셸을 만든다는 큰 방향은 요구에 적합하다. 다만 기존 계획을 그대로 실행하면 중복 구현, 레이아웃 폭 부족, 접근성 불일치, 작업공간 분리 문제가 발생한다. 따라서 구현 경로를 Astro 정적 프로젝트 하나로 통합하고 수치와 완료 조건을 구체화했다.

수정된 최종안은 [Kimjeongjae Wiki 최종 구현 계획](./wiki-visual-implementation-plan.md)이다.

## 발견 사항

### 1. 높음: HTML 프로토타입과 Astro 구현이 중복된다

기존 계획은 HTML/CSS로 두 페이지를 만든 뒤 Astro 컴포넌트로 이전한다. 이 과정에서 라우팅, asset 경로, 공통 레이아웃, 콘텐츠 주입 방식이 바뀌므로 외견을 다시 검증해야 한다. 프로토타입을 버리거나 유지할 이유도 생긴다.

수정: 처음부터 Astro `static` 출력으로 두 페이지만 구현한다. 외견 승인 전에는 기능과 문서 수를 늘리지 않는다. Astro는 기본적으로 페이지를 빌드 시 정적 HTML로 생성하므로 백엔드 부담은 추가되지 않는다. [Astro Configuration Reference](https://docs.astro.build/en/reference/configuration-reference/#output)

### 2. 높음: 현재 작업공간과 계획한 기술 스택이 다르다

현재 작업공간 루트에는 Git 저장소가 없고, `site/`에만 중첩 Git 저장소가 있다. `site/`는 Astro가 아니라 Next, React, Vinext, Drizzle, Cloudflare 관련 패키지를 포함한다. `node_modules`도 부분 설치된 상태다. 그대로 사용하면 문서와 사이트 변경 이력이 분리되고, 요구에 필요 없는 런타임과 패키지를 유지하게 된다.

수정: 구현 착수 시 `site/` starter를 제거하고 루트를 하나의 Git 저장소와 Astro 프로젝트로 정리한다. `docs/`는 보존한다.

### 3. 높음: 기존 3열 폭 규칙은 1200px에서 성립하지 않는다

중앙 760~900px에 좌측 탐색, 우측 목차, 열 간격과 페이지 여백을 더하면 1200px를 초과한다. 실제 구현에서는 본문이 눌리거나 가로 overflow가 발생한다.

수정: 3열 전환점을 1360px로 올리고 열 폭을 `176px / 최대 900px / 196px`로 고정한다. 960~1359px는 2열, 959px 이하는 단일 열로 전환한다.

### 4. 중간: 정보상자와 우측 목차가 동시에 본문을 압박한다

중앙 폭이 좁은 상태에서 정보상자를 300px로 float하면 첫 문단의 실제 읽기 폭이 400px 전후로 줄어든다. 뷰포트 기준 breakpoint만으로는 좌측 탐색 유무에 따른 중앙 폭을 정확히 알 수 없다.

수정: 정보상자는 문서 컨테이너가 820px 이상일 때만 우측 배치하고, 그보다 좁으면 첫 문단 다음에 전체 폭으로 내린다.

### 5. 중간: `aria-disabled`만으로 가짜 링크를 막을 수 없다

기존 계획은 아직 없는 기능에 `aria-disabled` 사용을 제안했다. 하지만 `href`가 있는 링크에 `aria-disabled="true"`를 붙여도 브라우저 동작은 막히지 않는다. W3C도 비활성 링크에는 `href`를 제거하는 방식을 안내한다. [W3C ARIA in HTML](https://www.w3.org/TR/html-aria/)

수정: 아직 없는 문서는 비활성 텍스트로, 비활성 검색 버튼은 네이티브 `disabled`로 구현한다. 현재 문서와 실제 링크만 키보드 포커스를 받는다.

### 6. 중간: placeholder 콘텐츠만으로는 레이아웃 내구성을 검증하기 어렵다

짧은 예시 문장만 사용하면 긴 한글 제목, 긴 URL, 넓은 프로젝트 표, 많은 분류가 들어왔을 때 발생할 문제를 놓친다.

수정: 릴리스 A부터 실제 문서 길이에 가까운 한국어 초안, 긴 프로젝트명, URL, 표와 각주를 포함한다. 콘텐츠는 초안이어도 레이아웃 입력값은 실제와 비슷하게 만든다.

### 7. 중간: 주요 시각 결정이 미확정 상태였다

현재형/고전형 레이아웃, 표기 언어, 로고 방식이 구현 직전 결정으로 남아 있었다. 이 세 항목은 헤더 폭, 글꼴, 반응형 동작에 직접 영향을 준다.

수정: 현대적인 Wiki 레이아웃, 한국어 중심 표기, 별도 로고 없는 텍스트 워드마크로 기본값을 확정했다.

### 8. 낮음: 검색이 너무 일찍 계획되어 있었다

Pagefind는 정적 사이트가 빌드된 뒤 출력 HTML을 인덱싱한다. 외견용 두 페이지 단계에서는 설치와 build 후처리만 늘고 검증 가치는 작다. [Pagefind Getting Started](https://pagefind.app/docs/)

수정: 검색 UI의 외견만 릴리스 A에 포함하고, 실제 Pagefind 검색은 문서가 확장되는 릴리스 B에서 추가한다.

### 9. 낮음: CSS와 자산 구조가 필요 이상으로 미리 분리되어 있었다

초기 두 페이지에 `tokens.css`, `wiki-shell.css`, `article.css`, `responsive.css`를 모두 만들면 작은 변경도 여러 파일을 오가게 된다. `brand-mark.*`도 실제 자산 형식이 정해지지 않은 표현이다.

수정: 초기 CSS는 `wiki.css` 하나로 시작하고, 별도 로고 자산 없이 텍스트 워드마크만 사용한다. 파일 분리는 복잡도가 실제로 생긴 뒤 진행한다.

## 구현 가능성 판단

수정된 계획에는 기술적 blocker가 없다. 정적 Astro 빌드, Markdown 문서, CSS Grid와 container query, 네이티브 `<details>` 메뉴만으로 릴리스 A를 구현할 수 있다. MediaWiki, 데이터베이스, 로그인, 서버 렌더링은 필요하지 않다.

남은 외부 입력은 실제 프로필 이미지와 포트폴리오 내용뿐이다. 이 자료가 없어도 텍스트 정보상자와 현실적인 초안 콘텐츠로 외견 승인본까지 구현할 수 있다.
