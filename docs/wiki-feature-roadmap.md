# Kimjeongjae Wiki 기능 로드맵 초안

작성일: 2026-07-14  
상태: 초기 계획 0.2, 편집기 요구 반영  
선행 문서: [최종 외견 구현 계획](./wiki-visual-implementation-plan.md)

## 1. 초기 요청 리마인드

`Kimjeongjae Wiki`의 출발점은 위키백과와 비슷한 룩과 사용 감각을 가진 개인 포트폴리오다. 이후 검토를 거쳐 다음 조건으로 구체화했다.

- 화면은 현대적인 Wiki 레이아웃과 고전적인 백과사전 조판을 결합한다.
- 외부 백과사전의 이름, 로고, 워드마크는 사용하지 않고 일반 명칭을 `Wiki`로 통일한다.
- 실제 다중 사용자 Wiki가 아니라 김정재 한 사람이 작성하고 관리하는 포트폴리오다.
- MediaWiki, 데이터베이스, 로그인 서버 없이 정적 사이트로 가볍게 운영한다.
- 문서 작성 방식은 처음 요청에서 특정하지 않았다. Markdown이나 Git 직접 수정은 사용자 요구가 아니라 초기 계획의 가정이었다.
- 공개 사이트는 정적으로 유지하되, 운영자는 실제 문서 편집 화면에서 콘텐츠와 이미지를 관리할 수 있어야 한다.
- 기능보다 외견을 먼저 승인한 뒤 필요한 운영 기능만 단계적으로 추가한다.

현재 릴리스 A에는 대문, 김정재 문서, 공통 Wiki 셸, 정보상자, 목차, 표, 각주, 분류와 반응형 레이아웃이 구현되어 있다. 현재 콘텐츠 파일이 Markdown인 것은 외견 프로토타입의 구현 방식일 뿐 최종 작성 경험으로 확정하지 않는다. 편집기, 검색, 최근 변경, 원본 보기, 역사 보기와 추가 문서는 아직 실제 기능이 아니다.

## 2. 제품 원칙

1. 방문자는 일반 포트폴리오가 아니라 연결된 Wiki 문서를 탐색한다고 느껴야 한다.
2. 운영자는 원문 파일이나 Git 명령을 몰라도 문서를 생성, 편집, 미리보기, 발행할 수 있어야 한다.
3. 서버 기능이 꼭 필요한 요구가 생기기 전까지 정적 출력 구조를 유지한다.
4. 화면에 노출한 기능은 실제로 작동해야 하며, 준비되지 않은 항목은 비활성 상태를 유지한다.
5. 저장 형식과 버전 관리 방식은 편집기 뒤에 감추고 운영 화면에는 문서 중심의 용어만 표시한다.

## 4. 문서 편집기

운영의 기본 흐름은 다음과 같이 수정한다.

```text
로컬 편집기 열기
  -> 문서 목록에서 새 문서 선택
  -> 시각 편집기로 본문과 정보 입력
  -> 이미지 첨부와 문서 블록 배치
  -> Wiki 화면 그대로 미리보기
  -> 초안 저장 또는 발행
  -> 최근 변경과 공개 사이트 갱신
```

편집기는 최소한 다음 화면을 제공한다.

- 문서 목록: 검색, 종류, 초안·발행 상태, 수정일
- 새 문서: 제목, URL ID, 문서 종류 선택
- 본문 편집: 제목, 문단, 굵게, 기울임, 링크, 목록, 인용, 코드, 표, 각주
- 구조 편집: 정보상자, 이미지, 갤러리, 안내 상자, 관련 문서 블록
- 미디어: 파일 선택과 드래그 앤 드롭, 미리보기, 대체 텍스트, 캡션
- 문서 설정: 카테고리, 관련 문서, 대표 문서, 공개일
- 미리보기와 발행: 실제 Wiki 조판으로 확인한 뒤 저장

레이아웃은 자유 좌표 배치가 아니라 Wiki 외형을 유지하는 구조화된 블록으로 제공한다. 예를 들어 이미지는 본문 폭, 우측 정렬, 갤러리 중 하나를 선택하고 정보상자는 정해진 필드를 추가·정렬하는 방식이다. 이렇게 해야 모바일에서도 문서가 깨지지 않는다.

저장 형식은 편집기의 내부 구현으로 취급한다. Markdoc, MDX 또는 구조화 JSON을 사용할 수 있지만 운영자가 원문을 직접 수정할 필요는 없다. 이미지도 편집기가 지정된 자산 폴더에 저장하고 공개 빌드에서 자동 최적화한다.

### 편집기 기술 후보

| 선택지 | 장점 | 제약 | 판단 |
| --- | --- | --- | --- |
| Keystatic 로컬 편집기 | Astro 연동, 문서 필드, 이미지 업로드, 구조화 블록을 빠르게 제공 | 기본 UI가 Wiki 편집 화면과 같지는 않으며 온라인 배포 시 Node 인증 환경 필요 | 1차 프로토타입 권장 |
| TipTap 기반 전용 편집기 | 실제 Wiki 화면 안에서 편집하는 경험과 툴바를 직접 설계 가능 | 저장 API, 이미지 처리, revision UI를 직접 구현해야 함 | 편집 경험이 최우선이면 채택 |
| MediaWiki VisualEditor | 실제 Wiki 편집, 템플릿과 revision 기능이 이미 존재 | PHP, 데이터베이스, MediaWiki 운영이 다시 필요 | 가벼운 운영 조건과 충돌 |

권장안은 먼저 로컬 전용 편집기 프로토타입으로 `문서 생성`, `이미지 삽입`, `정보상자와 표 편집`, `저장 후 재열기`를 검증하는 것이다. Keystatic의 편집 경험이 요구에 미치지 못하면 TipTap 기반 전용 편집기로 전환한다. 공개 사이트는 어느 경우에도 정적 출력으로 유지한다.

## 5. 최근 변경과 역사

최근 변경은 대문에 직접 적은 목록을 없애고 편집기의 저장·발행 기록에서 생성한다.

1. 편집기가 발행 시각, 문서 ID, 변경 종류와 수정 요약을 revision 기록으로 저장한다.
2. 발행된 문서와 revision 기록을 빌드가 읽을 수 있는 데이터로 변환한다.
3. 대문에는 최근 항목만 표시하고 전체 목록 페이지를 별도로 만든다.
4. 각 항목은 변경된 문서와 해당 문서의 역사 화면으로 연결한다.

Git을 사용하더라도 운영자가 직접 명령을 실행하는 흐름으로 만들지 않는다. 발행 과정이 필요한 파일 저장과 버전 기록을 처리하고, Git은 백업과 배포를 위한 내부 수단으로만 사용할 수 있다. revision의 실제 저장 방식을 파일 snapshot으로 할지 Git commit으로 할지는 편집기 프로토타입에서 결정한다.

공개 변경 이력은 문서 발행 기록으로 제한한다. 스타일이나 빌드 설정 변경은 대문의 최근 변경에 포함하지 않는다. 수정 요약과 이전 revision을 공개할지 여부는 운영 설정으로 둔다.

## 6. 검색과 문서 연결

Pagefind는 정적 HTML 생성 뒤 실행한다. 검색 결과에는 제목, 요약, 문서 종류와 카테고리를 표시하고 초안 문서는 인덱스에서 제외한다. 일반 `astro dev` 출력에는 검색 인덱스가 없으므로 검색 검증은 production build와 preview를 사용한다.

문서 탐색 화면은 다음 세 가지로 구분한다.

- `/wiki/`: 공개된 모든 문서를 제목순 또는 최근 수정순으로 보는 목록
- `/wiki/category/[category]/`: 선택한 카테고리에 속한 문서 목록
- `/wiki/search/`: 검색어와 일치하는 제목 및 본문 결과

전체 문서 목록에는 제목, 짧은 설명, 문서 종류, 카테고리, 마지막 수정일을 표시한다. 초기 문서 수가 적을 때는 페이지네이션을 넣지 않고, 문서가 100개를 넘을 때 다시 검토한다.

문서 연결은 세 단계로 확장한다.

1. `related` metadata로 작성자가 명시한 관련 문서를 표시한다.
2. 카테고리별 자동 색인 페이지를 생성한다.
3. 문서 수가 충분해지면 본문 링크를 분석해 역링크를 생성한다.

역링크는 초기 필수 기능이 아니며 문서가 10개 이상이 된 뒤 도입 여부를 다시 판단한다.

## 7. 단계별 구현 순서

### 단계 0: 운영 기반 확정

- 외견 승인 여부 기록
- 로컬 전용 편집과 온라인 편집 중 초기 범위 확정
- Keystatic과 전용 편집기의 핵심 작성 흐름 프로토타입 비교
- 콘텐츠 저장 형식과 이미지 폴더 구조 결정
- 초안 콘텐츠를 실제 정보로 교체할 범위 결정

완료 조건: 원문 파일을 직접 만지지 않고 문서 하나를 생성, 편집, 이미지 첨부, 저장, 재열기 할 수 있다.

### 단계 1: 문서 편집기 기반

- 문서 관리와 새 문서 화면
- 시각 본문 편집과 구조화 블록
- 이미지 업로드와 미디어 필드
- 초안 저장, 미리보기, 발행
- 프로젝트 문서 1개로 전체 작성 흐름 검증

완료 조건: 운영자가 코드, Markdown, Git 명령 없이 새 문서를 만들고 발행할 수 있다.

### 단계 2: 실제 탐색 구조

- 사이드바를 콘텐츠 기반으로 자동 생성
- 모든 문서 목록과 제목순·최근 수정순 정렬 구현
- 프로젝트, 기술, 연표, 연락처 문서 추가
- 카테고리 페이지와 관련 문서 구현
- 없는 메뉴 항목 제거 또는 실제 링크로 전환

완료 조건: 모든 노출 메뉴가 실제 페이지로 연결되고, 방문자가 목록만으로 전체 문서를 탐색할 수 있다.

### 단계 3: 변경 추적

- 편집기 revision 저장과 수정 요약
- 최근 변경 전체 페이지
- 문서별 역사 보기와 이전 revision
- `마지막 수정` 표시와 발행 기록 일치 검증

완료 조건: 편집기에서 문서를 발행하면 최근 변경, 역사와 수정일이 자동 갱신된다.

### 단계 4: 검색

- Pagefind 설치와 build 후처리
- 헤더 검색 입력과 `/wiki/search/` 결과 화면 구현
- 검색어, 결과 없음, 로딩, 오류 상태와 키보드 동작 구현
- 초안과 비본문 영역 인덱싱 제외
- production preview용 검색 검증 명령 추가

완료 조건: 제목과 본문 검색으로 원하는 문서를 찾을 수 있다.

### 단계 5: 배포와 공개 품질

- GitHub Actions와 GitHub Pages 배포
- canonical URL, sitemap, robots, 소셜 공유 metadata
- 실제 프로젝트 이미지 최적화
- 모바일, 키보드, 링크, 검색 회귀 테스트

완료 조건: push만으로 검증과 배포가 완료되고 별도 서버 운영이 필요 없다.

## 8. 구현 전 확인사항

다음 결정은 단계 0에서 확정한다.

- GitHub 저장소를 공개할지 비공개로 유지할지
- GitHub Pages 기본 주소와 커스텀 도메인 사용 여부
- 편집기를 같은 컴퓨터에서만 사용할지 외부에서도 사용할지
- 기본 CMS 형태와 Wiki 화면 안의 직접 편집 중 어느 경험을 원하는지
- 공개 화면에서 수정 요약과 이전 revision을 노출할지
- 첫 프로젝트 3개와 실제 소개 문구
- 프로필 또는 프로젝트 대표 이미지 사용 여부

편집기의 사용 위치와 편집 경험은 단계 1 전에 정해야 한다. 저장소 공개 여부, 변경 이력 공개 범위와 도메인은 편집기 프로토타입 이후에 확정해도 된다.

## 9. 초기 우선순위 결론

다음 구현의 1순위는 검색이 아니라 **실제 문서 편집기 프로토타입**이다. 이미지와 구조화 블록을 포함한 문서를 편집기로 만들 수 있는지 먼저 확인해야 콘텐츠 형식과 나머지 기능을 안전하게 결정할 수 있다.

권장 순서는 `편집기 프로토타입 -> 저장 형식 확정 -> 프로젝트 문서 추가 -> 자동 탐색/카테고리 -> 최근 변경/역사 -> 검색 -> 배포`다. 이 순서라면 공개 사이트는 정적으로 유지하면서 작성 경험은 실제 Wiki에 가깝게 만들 수 있다.

## 10. 구현 가능성 검토

현재 Astro 정적 출력은 이 로드맵을 수용할 수 있다. 편집기는 로컬에서 파일과 이미지를 생성하고, 공개 빌드는 그 결과만 정적 HTML로 변환할 수 있다. Pagefind는 완성된 `dist/`를 읽어 정적 검색 bundle을 추가하고 GitHub Pages는 공개 결과물만 배포한다.

예상되는 문제와 대응은 다음과 같다.

| 문제 | 영향 | 대응 |
| --- | --- | --- |
| 편집기 방식이 미확정 | 콘텐츠 형식과 revision 설계를 확정할 수 없음 | 단계 0에서 핵심 작성 흐름 프로토타입 검증 |
| 온라인에서도 편집하려는 경우 | 인증과 쓰기 API가 필요 | 초기에는 localhost 전용, 필요 시 편집 서비스만 별도 배포 |
| Keystatic의 기본 UI가 Wiki와 다름 | 기대한 직접 편집 감각이 부족할 수 있음 | 승인되지 않으면 TipTap 전용 편집기로 전환 |
| 이미지 원본이 계속 누적 | 저장소와 빌드 크기 증가 | 업로드 시 크기 제한, 최적화, 사용하지 않는 자산 점검 |
| Pagefind는 build 후 생성 | 개발 서버에서 검색 파일 없음 | production build와 preview를 검색 QA 기준으로 사용 |
| revision 저장이 무제한 증가 | 역사 데이터가 불필요하게 커짐 | 발행 revision만 보존하고 자동 저장은 임시 데이터로 분리 |
| 초안이 메뉴나 검색에 섞일 수 있음 | 미완성 문서 공개 | route, menu, category, search에서 같은 `draft` 필터 공유 |
| 자동 메뉴의 순서가 불안정할 수 있음 | 탐색 순서가 빌드마다 달라짐 | `order` metadata와 문서 ID를 정렬 기준으로 사용 |

현재 확인된 기술적 blocker는 없다. 가장 큰 설계 리스크는 기본 CMS 화면으로 충분한지, 아니면 Wiki 본문을 직접 편집하는 전용 화면이 필요한지가 아직 정해지지 않은 점이다.
